# Практика 4. Додавання записів, встановлення ключів і зв'язків

**Варіант 5 — Автосалон.** Таблиці схеми: `cars` (вимір 1), `clients` (вимір 2), `sales` (фактова, два зовнішні ключі).

## Завдання 1. Увімкнення перевірки і таблиця-вимір 2

Першим рядком сеансу виконано `PRAGMA foreign_keys = ON;`. Перевірка, що прапорець справді увімкнено на цьому з'єднанні: `PRAGMA foreign_keys;` повертає `1`.

Створено таблицю-вимір 2 — `clients`:

| стовпець | тип | чому саме він |
|---|---|---|
| `id` | INTEGER PRIMARY KEY | псевдонім `rowid`, автоінкремент, унікальний ідентифікатор клієнта |
| `last_name` | TEXT NOT NULL | прізвище — рядок, обов'язкове |
| `first_name` | TEXT NOT NULL | ім'я — рядок, обов'язкове |
| `phone` | TEXT | номер не використовується в обчисленнях, має `+`, провідні нулі й довжину > 15 цифр — це текст, а не INTEGER |
| `city` | TEXT | місто клієнта |

`clients` жодного разу не посилається на `cars` — обидві вимірні таблиці незалежні й зв'язуються тільки через фактову.

## Завдання 2. Фактова таблиця з двома FOREIGN KEY

```sql
CREATE TABLE sales (
    id             INTEGER PRIMARY KEY,
    car_id         INTEGER NOT NULL,
    client_id      INTEGER,
    sale_date      TEXT NOT NULL,
    price          REAL NOT NULL,
    payment_method TEXT NOT NULL DEFAULT 'готівка',
    FOREIGN KEY (car_id)    REFERENCES cars (id)    ON DELETE RESTRICT,
    FOREIGN KEY (client_id) REFERENCES clients (id) ON DELETE SET NULL
);
```

**`car_id → cars(id)`: `ON DELETE RESTRICT`.** Продаж без автомобіля не має сенсу: саме автомобіль визначає, що було продано і за що надійшли гроші. Якщо дозволити видалити рядок з `cars`, на який посилається продаж, то з `CASCADE` разом з автомобілем зникне й фінансовий запис (втрата бухгалтерської історії), а з `SET NULL` залишиться продаж «невідомо чого». `RESTRICT` перетворює таку спробу на явну помилку: спершу розберися з проданими одиницями, а вже потім видаляй позицію з каталогу. Тому `car_id` ще й `NOT NULL` — порожнім він бути не може за визначенням.

**`client_id → clients(id)`: `ON DELETE SET NULL`.** Тут бізнес-сенс протилежний. Клієнт може попросити видалити свої персональні дані (прізвище, телефон), і автосалон зобов'язаний це зробити — але сам факт продажу нікуди не дівається: гроші отримані, авто відвантажене, запис потрібен для звітності й гарантійного обліку. `CASCADE` тут був би прямою втратою виручки зі звітів, `RESTRICT` — забороною видалити персональні дані взагалі. `SET NULL` знеособлює продаж, зберігаючи його: `client_id` стає `NULL`, тому цей стовпець свідомо оголошений без `NOT NULL`.

Отже дії різні саме тому, що різні наслідки: автомобіль — предмет угоди (без нього угода безглузда), клієнт — сторона угоди (угода лишається дійсною і без його персональних даних).

## Завдання 3. Заповнення пов'язаними даними

Вставлено 6 рядків у `clients` і 10 рядків у `sales`. Усі `car_id` — з діапазону 1–6 (реальні `id` з `cars`), усі `client_id` — з діапазону 1–6 (реальні `id` з `clients`); вигаданих значень немає.

Повторювані `car_id` означають, що автосалон продає кілька екземплярів однієї позиції каталогу (наприклад, дві Toyota Corolla різним покупцям) — `cars` тут описує модельну позицію, а не один конкретний VIN.

Перевірка зв'язності:

```sql
SELECT c.brand, c.model, cl.last_name, s.sale_date, s.price
FROM sales s
JOIN cars c     ON c.id  = s.car_id
JOIN clients cl ON cl.id = s.client_id;
```

Запит повертає 10 рядків — жоден зовнішній ключ не «висить».

## Завдання 4. Навмисна помилка зовнішнього ключа

```sql
INSERT INTO sales (car_id, client_id, sale_date, price)
VALUES (9999, 1, '2026-07-01', 600000);
```

Точне повідомлення SQLite:

```
Error: FOREIGN KEY constraint failed
```

Рядок у таблицю не потрапив (`SELECT COUNT(*) FROM sales;` так само повертає 10). Це підтверджує, що `PRAGMA foreign_keys = ON;` діє на поточному з'єднанні: без неї цей самий `INSERT` виконався б без помилки й у `sales` з'явився б продаж автомобіля, якого не існує.

## Завдання 5. Звірка з ER-діаграмою Практики 3

Реалізовано рівно ту схему, що була спроєктована в Практиці 3: дві вимірні таблиці (`cars`, `clients`) і фактова `sales` з двома зовнішніми ключами `car_id → cars(id)` і `client_id → clients(id)`; обидва зв'язки — 1:N у напрямку від виміру до факту; прямого зв'язку між `cars` і `clients` немає.

Зміни щодо діаграми:

- `client_id` у фактовій таблиці залишено **без** `NOT NULL` — це вимушений наслідок обраного `ON DELETE SET NULL` (SQLite не зміг би записати `NULL` у `NOT NULL`-стовпець і дія просто впала б з помилкою). На діаграмі цей нюанс не позначався, бо кардинальність від нього не змінюється.
- Додано `payment_method TEXT NOT NULL DEFAULT 'готівка'` як атрибут самої угоди — він описує факт продажу, а не автомобіль і не клієнта, тож належить саме фактовій таблиці.

Інших розбіжностей (назви таблиць, назви стовпців, напрямки FK) немає.

## Відповіді на контрольні питання

**Навіщо `PRAGMA foreign_keys = ON;`, якщо `FOREIGN KEY` оголошений у `CREATE TABLE`?** З історичних причин сумісності SQLite за замовчуванням оголошені зовнішні ключі *не перевіряє* — вони зберігаються у схемі як декларація, але не як обмеження. Прапорець вмикається для конкретного з'єднання й не зберігається у файлі `.db`, тому кожен новий сеанс (нове відкриття в DB Browser, новий запуск `sqlite3`) починається знову з вимкненою перевіркою.

**Різниця між PRIMARY KEY і FOREIGN KEY.** `PRIMARY KEY` ідентифікує рядок усередині своєї таблиці — унікальне, незмінне «ім'я» запису (`cars.id`). `FOREIGN KEY` нічого не ідентифікує: він посилається на первинний ключ іншої таблиці й гарантує, що значення справді там існує (`sales.car_id` мусить збігтися з якимось `cars.id`).

**`CASCADE` проти `RESTRICT`.** `CASCADE` видаляє залежні рядки разом із батьківським — видалили клієнта, зникли і його продажі. `RESTRICT` навпаки забороняє видалення батьківського рядка, доки на нього хтось посилається. Різні студенти можуть обґрунтовано обрати різне для одного зв'язку, бо вибір диктує не SQL, а бізнес-правило: якщо продаж — фінансовий документ, його не можна втрачати (`RESTRICT`/`SET NULL`); якщо це технічний журнал, який без батьківського запису безглуздий, доречний `CASCADE`.
