# Практика 15. Індекси та аналіз плану запиту

**Варіант 5 — Автосалон.** Індекси побудовано на фактовій таблиці `sales` у базі після практики 14.

## Завдання 1. План до індексу

```sql
EXPLAIN QUERY PLAN
SELECT * FROM sales WHERE client_id = 2;
```

Точний план до будь-якого індексу:

```
SCAN sales
```

`client_id` є зовнішнім ключем на `clients`, але SQLite не створює індекс за зовнішнім ключем сама. Фільтр читає всю таблицю.

## Завдання 2. Як змінився план

```sql
CREATE INDEX idx_sales_client ON sales(client_id);
```

Той самий запит після індексу:

```
SEARCH sales USING INDEX idx_sales_client (client_id=?)
```

`SCAN sales` замінився на пошук по індексу `idx_sales_client`. SQLite іде в індекс за рівністю `client_id = 2` і дістає тільки відповідні рядки, а не переглядає всю таблицю.

## Завдання 3. Композитний індекс

Запит з двома умовами до композитного індексу використовував лише індекс завдання 2:

```
SEARCH sales USING INDEX idx_sales_client (client_id=?)
```

Індекс знаходить продажі клієнта, а умову `payment_method = 'кредит'` SQLite перевіряє вже на знайдених рядках. Після

```sql
CREATE INDEX idx_sales_client_payment ON sales(client_id, payment_method);
```

план став:

```
SEARCH sales USING INDEX idx_sales_client_payment (client_id=? AND payment_method=?)
```

Обидві рівності тепер закриває сам індекс. Одноколонковий індекс дає менший ефект, бо друга умова лишається фільтром після пошуку. Композитний індекс у порядку `(client_id, payment_method)` відповідає обом умовам одразу. Порядок колонок важливий: індекс можна використати з лівого краю, тому він також придатний для запиту лише за `client_id`.

## Завдання 4. ORDER BY за датою

До індексу план сортування був:

```
SCAN sales
USE TEMP B-TREE FOR ORDER BY
```

`USE TEMP B-TREE FOR ORDER BY` означає окреме сортування результату. Після `CREATE INDEX idx_sales_date ON sales(sale_date)` план став:

```
SCAN sales USING INDEX idx_sales_date
```

Кроку сортування більше немає: індекс уже тримає рядки в порядку `sale_date`, і таблицю можна читати в цьому порядку.

## Завдання 5. Видалення індексу

Видалено `idx_sales_date`. План `ORDER BY sale_date` повернувся до:

```
SCAN sales
USE TEMP B-TREE FOR ORDER BY
```

Знову є повний перегляд і тимчасове сортування. `SELECT name FROM sqlite_master WHERE type = 'index'` більше не містить `idx_sales_date`. Залишилися:

```
idx_sales_client
idx_sales_client_payment
```

## Відповіді на контрольні питання

**1. Чому EXPLAIN QUERY PLAN показує план, а не результат?** План описує, як SQLite збирається дістати рядки: повний перегляд, пошук по індексу чи окреме сортування. Результат запиту при цьому той самий. Перевіряти план треба окремо, бо повільний і швидкий варіант повертають однакові дані, і за самими рядками різницю не видно.

**2. Чому індекс лише на першій колонці слабший за композитний?** Індекс на `client_id` відсікає частину рядків, але `payment_method` доводиться перевіряти для кожного з них. Композитний індекс на `(client_id, payment_method)` одразу вказує на рядки, де істинні обидві умови, тож зайвого фільтру немає.

**3. Яка ціна індексу і чому не індексувати кожну колонку?** Індекс займає місце і оновлюється на кожному `INSERT`, `UPDATE` і `DELETE` проіндексованої колонки. Запис стає повільнішим, а зайві індекси оптимізатор може просто не використати. Індекс варто створювати під конкретний частий фільтр, з'єднання чи сортування, а не на кожну колонку про запас.
